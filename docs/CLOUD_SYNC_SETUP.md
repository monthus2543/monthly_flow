# ระบบซิงค์ Monthly Flow ผ่านบัญชี Google

## พฤติกรรมที่เพิ่ม

- เข้าบัญชี Google แล้วซิงค์ข้อมูลการเงินกับ Cloud Firestore ใน Firebase Project `monthly-flow-75287`
- ครั้งแรกนำข้อมูลโหมดตั้งชื่อเข้าบัญชี Google แรกของเครื่องโดยอัตโนมัติ เก็บต้นฉบับโหมดตั้งชื่อไว้ ไม่ลบทิ้ง
- การนำเข้าทำครั้งเดียวและรักษารหัสรายการเดิม จึงลองใหม่หลังแอปปิดกลางทางได้โดยไม่สร้างรายการซ้ำ
- แยกฐานข้อมูล SQLite ตาม Firebase UID การออกจากระบบกลับไปยังข้อมูลโหมดตั้งชื่อเดิม ข้อมูล Google ที่แก้หลังนำเข้าอยู่ในฐานข้อมูลบัญชีและคลาวด์
- บัญชี Google อื่นบนเครื่องเดียวกันเริ่มพื้นที่ของตนเอง ไม่ดึงข้อมูลส่วนตัวของบัญชีแรกเข้ามา
- ซิงค์รายรับรายจ่าย หมวดหมู่ กระเป๋าเงิน งบประมาณ รายการประจำ เป้าหมายออมเงิน และเตือนบิล
- บันทึกออฟไลน์ได้ คิวรอส่งเก็บถาวรใน SQLite และลองใหม่เมื่อออนไลน์/กลับเข้าแอป/กดซิงค์ตอนนี้
- หน้าบัญชีแสดงกำลังซิงค์ ซิงค์แล้ว ข้อมูลรอส่ง หรือซิงค์ไม่สำเร็จ
- PIN การตั้งค่าหน้าจอ ภาษา OAuth token และไฟล์รูปใบเสร็จไม่ส่งขึ้นคลาวด์ รูปยังเปิดได้บนเครื่องต้นทาง

## ก่อนใช้กับบัญชีจริง

ตรวจจาก Firebase Console เมื่อ 6 ตุลาคม 2026: สร้าง Cloud Firestore `(default)` ที่ `asia-southeast3` (กรุงเทพฯ) แล้ว และโปรเจกต์ Monthly Flow ยังใช้ Spark — No-cost ($0/month)

เผยแพร่ `firestore.rules` ของโปรเจกต์สำเร็จแล้ว ตรวจ Rules Playground ด้วย UID จำลอง: เจ้าของอ่านพื้นที่ตัวเองได้, ผู้ไม่ได้เข้าสู่ระบบและบัญชีอื่นอ่านไม่ได้, ข้อมูลผิดรูปแบบเขียนไม่ได้ และการลบเอกสารถาวรถูกปฏิเสธ การจำลองเหล่านี้ไม่ได้สร้างข้อมูลการเงินจริง

1. เปิด https://console.firebase.google.com/project/monthly-flow-75287/firestore
2. สร้าง Cloud Firestore **Standard edition** โดยใช้ `(default)` database เลือก location ก่อนสร้าง (เปลี่ยนที่เดิมภายหลังไม่ได้)
3. เริ่มใน Production mode แล้วนำเนื้อหาไฟล์ `firestore.rules` ของโปรเจกต์ไปตั้งในแท็บ Rules และ Publish
4. กฎอนุญาตเฉพาะผู้ใช้ Firebase ที่ UID ตรงกับ `/users/{uid}/finance/{recordId}` ห้ามเข้าข้อมูลของบัญชีอื่น และเก็บการลบเป็น tombstone
5. ไม่ต้องอัปเกรดเป็น Blaze สำหรับโค้ดรอบนี้ หากใช้ CLI ที่มีอยู่แล้วสามารถ deploy เฉพาะ rules ด้วย `firebase deploy --only firestore:rules --project monthly-flow-75287`
6. ติดตั้งแอปใหม่ที่รวม dependency Cloud Firestore แล้วทดสอบบัญชีจริงสองอุปกรณ์

ฐานข้อมูลและกฎถูกเปิดใช้แล้ว แต่ยังไม่ได้ทดสอบการเขียนด้วย server timestamp และการซิงค์บัญชีจริงระหว่างสองอุปกรณ์ ผลทดสอบแอปจำลอง 70 รายการผ่าน และ Flutter analyze ไม่พบปัญหา

## เมื่อแก้ข้อมูลพร้อมกัน

รายการต่างกันรวมกันได้ แม้หมายเลขแถว SQLite ของสองเครื่องตรงกัน เพราะใช้รหัสรายการคลาวด์แยกต่างหากและแปลงความสัมพันธ์หมวดหมู่/กระเป๋าเงิน

ถ้าแก้ **รายการเดียวกัน** สองเครื่อง ใช้ข้อมูลที่เขียนถึงเซิร์ฟเวอร์ล่าสุด ไม่ได้รวมแต่ละช่องหรือแสดงประวัติความขัดแย้ง การลบชนะการแก้ที่ค้างบนเครื่องอื่นเพื่อไม่ให้รายการที่ลบกลับมา การคืนรายการจาก backup สร้างตัวตนใหม่

งบประมาณเดือน/หมวดเดียวกันและรายการประจำของกฎ/เดือนเดียวกันใช้รหัสร่วมกันเพื่อป้องกันรายการซ้ำ

## ข้อจำกัดปัจจุบัน

- ซิงค์ขณะแอปทำงานหรือกลับมาใช้งาน ไม่รับประกันงานขณะระบบปิดแอปเบื้องหลัง
- รูปใบเสร็จยังไม่ซิงค์ ไม่มีการลบบัญชีคลาวด์/กู้รายการที่ลบ/ประวัติการแก้ไข
- ใช้ listener และอ่านรายการบัญชีทั้งหมดในแต่ละรอบ; ต้องปรับ incremental sync หากข้อมูลมีจำนวนมาก Cloud Firestore มีโควตา/ค่าบริการตามแผน
- เก็บ tombstone เพื่อรองรับเครื่องที่ออฟไลน์นาน ไม่ลบทิ้งอัตโนมัติ
- ตรวจสิทธิ์อ่านและกรณีปฏิเสธใน Rules Playground แล้ว ยังไม่ได้ทดสอบ Security Rules ด้วย Firebase emulator หรือทดสอบข้อมูลถูกต้องที่ใช้ server timestamp บนอุปกรณ์จริง

## ตรวจรับบนอุปกรณ์จริง

1. เครื่อง A สร้างข้อมูลแบบตั้งชื่อ แล้ว Google login: ข้อมูลเดิมยังอยู่และสถานะซิงค์แล้ว
2. เครื่อง B login บัญชีเดียวกัน: เห็นข้อมูลตรงกัน หมวดหมู่และกระเป๋าเงินถูกต้อง
3. ปิดอินเทอร์เน็ต A เพิ่ม/แก้/ลบข้อมูล ปิดแล้วเปิดแอปใหม่ จากนั้นเปิดเน็ตและตรวจ B
4. ลบรายการบน A ขณะที่ B ออฟไลน์แก้รายการนั้น: รายการไม่กลับมาหลัง B ซิงค์
5. ออกจากระบบและเข้าบัญชี Google อื่น: ไม่เห็นข้อมูลบัญชีแรก
6. รหัส PIN เดิมยังทำงาน และไม่มี PIN/token/path รูปใบเสร็จอยู่ใน Firestore
7. ตรวจ Rules ว่าบัญชีอื่นและผู้ไม่ได้เข้าสู่ระบบอ่านหรือเขียน UID นี้ไม่ได้
